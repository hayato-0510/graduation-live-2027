# 開発の流れ

1つの作業が、始まってから本番に反映されるまでの全行程。
用語は出てきた所で説明する。

## 全体像

Issue（やること）→ ブランチ → 変更 → ローカル確認 → Pull Request（dev 宛て）→ プレビュー確認 → レビュー → dev にマージ → 昇格 PR → 本番反映

## 1. Issue を見る

Issue は「やること」の一覧（GitHub の Issues タブ）。作業は Issue 単位で取る。
段階ラベルが付いているので、自分の段階のものから取る。段階の意味は [dev-guide.md](dev-guide.md) の「4. 作業の段階」。

## 2. ブランチを切る

dev から作業用ブランチを切る。ルールと名前の付け方は [branch-rules.md](branch-rules.md)。

## 3. 変更する

- コンテンツ（バンド、タイムテーブル、日程など）は `src/data/` の JSON を直す
- 見た目は `src/` のコンポーネントと CSS
- 途中で保存したい時はこまめに commit（変更の記録）して push（GitHub への送信）する。push した時点で下書きとして残るので、PC が壊れても作業は消えない

## 4. ローカルで確認する

自分の PC で次が全部通ることを確認する。

| コマンド               | 何を見ているか                         |
| ---------------------- | -------------------------------------- |
| `npm run format:check` | 書き方の整形がルール通りか             |
| `npm run validate`     | `src/data/` の JSON が決めた形式通りか |
| `npm run check`        | TypeScript の型のミスが無いか          |
| `npm run build`        | 本番用のファイルが正しく作れるか       |

整形が崩れていたら `npm run format` で直せる。

## 5. Pull Request を作る

Pull Request（PR）は「この変更を dev に入れてよいですか」という申請。宛先（base）が dev になっているか最初に確認する。
テンプレートに沿って、変更内容と自分の段階にチェックを入れて書く。

PR を作ると自動で2つ起きる。

- **CI**（自動検査）が走る。上の表の検査を GitHub 側でもう一度全部やる。1つでも失敗すると赤くなり、その PR はマージできない
- **プレビュー**ができる。数分後に PR コメントへプレビュー URL が自動で付き、変更後のサイトを本番とは別の URL で見られる

## 6. プレビューで確認する

- プレビュー URL を開いて、自分の変更が意図通りか見る
- スマホ幅（375px 前後）でも崩れていないか見る
- リンクが全部生きているか押してみる
- UI を変えた場合はスクリーンショットを撮って PR に貼る（文章より1枚の絵の方が速く伝わる）

## 7. レビュー

他の人が PR を読んで確認する工程。

- 段階1・2は、CI が緑でプレビュー確認が済んでいれば進めてよい
- 段階3（共通部品）は、始める前に主催者へ一言＋レビュー必須
- 指摘が付いたら直して push する。同じ PR に自動で反映され、CI も回り直す
- 会話が残っている PR はマージできない決まり（解決済みにしてから）

## 8. dev にマージ

マージすると変更が dev に入る。dev のプレビュー URL（https://dev.graduation-live-2027.pages.dev/）で、他の人の変更と合体した状態を確認できる。ここまでが普段の作業の完了。
マージ後の後片付けは [branch-rules.md](branch-rules.md)。

## 9. 本番へ出す（昇格）

本番に出すタイミングで、dev → main の Pull Request（昇格 PR）を1本作る。dev に溜まった変更がまとめて本番に出る。

- 昇格 PR でも CI が全部緑であることが必要
- マージすると Cloudflare Pages が自動で本番を更新する（数分）。本番 URL で最終確認したら完了
- 本番で問題が起きた時の戻し方は [operations.md](operations.md)
