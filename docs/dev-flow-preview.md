## 結論

1. **「dev環境」は、常駐する1本の開発用ブランチではなく、PRごとのプレビューにする。** PRを作るたびにそのPR専用のURLが生え、閉じれば消える。これが「完全な開発環境として提供する」の実体にする。開発用ブランチを1本長く持つ方式は、初心者がいる体制では差分が膨らんで衝突の元になるので採らない。
2. **プレビューの仕組みは高専祭HPと同方式にする**（後述の方式B: GitHub Actions + Wrangler で Cloudflare Pages へデプロイし、プレビューURLをPRコメントに自動投稿）。理由は「高専祭と同じように」という指定そのものと、春平が高専祭コードと見比べながら学べる一貫性。
3. **高専祭の重い部分は今は真似しない。** ページ単位のE2E自動選別、毎晩の全ページ検査、`release.json` による公開制御は、高専祭では大人数・多ページゆえの仕組み。卒業ライブはページ数も人数も少ないので、最初は「CI（check + build）→ デプロイ → PRコメント」の1本道だけを作り、必要になったら足す。
4. **初心者の作業は段階に分ける。** 最初はデータ（JSON）と文章の編集だけ、次に部品のコピー改変、共通部品（レイアウト・全体CSS・ヘッダー）は事前に一言かけてから触る。高専祭の共同作業ルールと同じ考え方。
5. **移行には君の手が1回だけ要る。** Cloudflare のAPIトークン作成はダッシュボード側の操作で、Muse のブラウザは Turnstile で弾かれるため代行できない。トークンとアカウントIDを GitHub Secrets に登録するところまでが君の分担、その先のワークフロー実装・切替・検証は Muse が PR でやる。

## まず言葉の整理

初めての人向けに、この設計書で使う言葉を先に置く。

- **ブランチ**: リポジトリのコピーの枝。本番（main）を汚さずに作業するための作業場。1つの作業に1本切る。
- **PR（Pull Request）**: 「この枝の変更を main に取り込んでください」という申請ページ。変更内容の確認、会話、チェック結果、プレビューリンクが全部ここに集まる。作業の記録はチャットに散らさず PR に残す。
- **CI**: PRのたびに自動で走る検査。今は `astro check`（型の間違い探し）と `astro build`（サイトが組み立てられるか）の2つ。赤くなったらマージできない設定済み。
- **デプロイ**: ビルドしたサイトを公開サーバーに置くこと。
- **プレビュー（dev環境）**: PR専用に一時公開されるサイト。URLを知っている人だけが見る前提だが、技術的には公開URLなので、未発表情報は本番同様に載せない。
- **本番（production）**: main にマージされたものが公開される正式なサイト。

## 高専祭HPの実物確認（2026-11-13、公開リポジトリ `suzuka-kosen-festa/2026-hp` で検証）

「高専祭と同じように」の中身を、README と `.github/workflows/deploy.yml` と `AGENTS.md` の実物で確認した。

- 本番は Cloudflare Pages: `snct-fes-2026.pages.dev`（独自ドメイン `snct-fes.info` を被せている）。main への push で自動デプロイ。
- PR を作ると GitHub Actions が build して Cloudflare Pages へデプロイし、**PRのコメントにプレビューURLを自動投稿する**（README の「デプロイ・プレビュー」節に明記）。レビューはそのURLを開いて行う決まり。
- 実装は Cloudflare の Git連携ではなく **GitHub Actions + `cloudflare/wrangler-action`** 方式。デプロイごとに固有のURL（deployment-url）が払い出され、ワークフローが `gh pr comment --edit-last` で1本のコメントを使い回して更新する。本文にはコミット番号と更新時刻（JST）を入れて、古いプレビューとの見間違いを防いでいる。加えて、PR下部のチェック欄にもプレビューURLをコミットステータスとして出す。
- 認証は GitHub Secrets の `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID`。Pages プロジェクトが無ければ作るステップまでワークフローに入っている（失敗しても続行）。
- ビルドは `TZ: Asia/Tokyo` で回す。日付判定（お知らせの表示日など）を UTC でやると朝9時前にずれる、という実地の教訓。
- 共同作業は GitHub Flow: main 直 push 禁止、`feature/xxx` ブランチ → PR → レビュー後マージ。担当はページ単位で分け、共通部品を触るときは事前に Discord で一言。Node は `.node-version` で固定し、CI も同じファイルを読む。依存を変えないときは `npm install` ではなく `npm ci`（ロックファイルを書き換えて余計な差分を作らないため）。
- 作業者向けの確認作法: スマホファースト、プレビューは 375px 幅で確認してから PC 幅を見る。

卒業ライブ側の現状との差分は次の通り。今の `graduation-live-2027` は GitHub Pages に main マージでデプロイするだけで、PRプレビューは無い。Node は `package.json` の engines（>=24 <25）と CI の指定（24）で言い方が揃っておらず、`.node-version` ファイルも無い。ここも移行PRで高専祭方式に揃える。

## 方式の選択

### 方式A: Cloudflare Pages の Git連携

Cloudflare のダッシュボードで GitHub リポジトリを接続すると、main への push で本番、他のブランチや PR でプレビューが自動で生える。プレビューURLはブランチ名ベースで予測できる。ワークフローのコードは要らず、Secrets の管理も無い。

- 長所: 仕組みが一番単純。保守するコードが増えない。
- 短所: PRコメントへの自動投稿は Cloudflare 側の連携任せになり、高専祭の「PRを開けばコメントにリンクがある」という体験と一致するとは限らない。デプロイの細かい制御（CIが通ったものだけ出す等）も効きにくい。接続作業はダッシュボードで君がやる必要がある。

### 方式B: GitHub Actions + Wrangler（高専祭と同方式）← 採用

今の CI と同じ GitHub Actions の中でビルドし、`cloudflare/wrangler-action` で Cloudflare Pages へデプロイする。PR のときはプレビューURLをコメントとコミットステータスに出す。

- 長所: 高専祭と体験もコードも揃う。CI が通ったものだけデプロイする、という順番をワークフローで保証できる。将来 E2E を足すときも高専祭の型をそのまま持ってこられる。
- 短所: APIトークンの発行と Secrets 登録という初回作業が要る。ワークフロー自体が保守対象になる（ただし高専祭の実物が手本になる）。

### 採らない方式

- **開発用ブランチ（dev）を1本常駐させる**: 「devに向けてPRを出す」と聞こえは良いが、main との差分が育ち続け、マージのたびに初心者が衝突解決を背負う。PRごとのプレビューで dev の役割は代替できる。
- **GitHub Pages のままプレビューを自作する**（プレビュー用フォルダへ成果物を置く等）: 動かなくはないが独自仕組みの保守が増え、高専祭とも揃わない。

## 環境の定義

| 環境 | 実体 | いつ更新されるか | URL | 誰が見るか |
|---|---|---|---|---|
| ローカル | 自分のPC上の開発サーバー | 自分が保存するたび | `http://localhost:4321` | 自分だけ |
| プレビュー（dev） | PRごとの Cloudflare Pages 一時デプロイ | PRに push するたび自動 | PRコメントに投稿される固有URL | PRを知っているメンバー |
| 本番 | main の Cloudflare Pages デプロイ | main へマージするたび自動 | `graduation-live-2027.pages.dev`（予定） | 全員（公開） |
